01 Professional Ethics & Risk Management High Yield
★ Frequently tested — know all 8 principles + 3 risk types

Software Engineering Code of Ethics (IEEE-CS/ACM)

Developed by the IEEE-CS/ACM Joint Task Force (SEEPP) to guide moral decisions in software work. It is not an algorithm — you use your judgment within these principles.

"PC PM JC Self"

Public → Client & Employer → Product → Management → Judgement → Colleagues → Profession → Self

#PrincipleKey Idea
1PublicAct in public interest; health, safety, welfare
2Client & EmployerBest interests of client, consistent with public interest
3ProductHighest professional standards
4JudgementMaintain integrity & independence
5ManagementPromote ethical management approach
6ProfessionAdvance integrity and reputation
7ColleaguesBe fair and supportive
8SelfLifelong learning; ethical practice

Risk Management — The 3 Key Questions

1. What can go wrong?  |  2. What is the potential damage?  |  3. What can we do about it?

Risk Identification

Definition: A risk = uncertain future event with possible unwanted consequences.

By EffectDefinitionExample
Project RiskThreatens project schedule/costTeam member leaves; unrealistic deadline
Technical RiskThreatens product quality/timelinessNew unproven technology used
Business RiskThreatens product viabilityMarket changes; competitor launches first
By NatureDefinitionExample
Known RiskIdentified via careful evaluationUnrealistic delivery date
Predictable RiskExtrapolated from past experiencePrevious employee turnover rate
Unpredictable RiskVery hard to identify in advanceNatural disaster, global pandemic

Risk Estimation (Projection)

Rate each risk by: (1) Likelihood and (2) Consequence/Severity. Then rank risks by priority.

Risk Prevention Strategies

✅ Proactive Strategy

  • Avoid risks before they happen
  • Devise contingency plans for unavoidable risks
  • Called "disaster prevention"

⚠️ Reactive Strategy

  • Do nothing until problem occurs
  • Rush to fix when it happens
  • Called "firefighting"
Identify → Estimate → Plan → Prevent → Control (then loop)

4 P's of Project Management

People (contributors) · Product (software built) · Process (SE activities) · Project (all efforts for success)

Project Participants / Stakeholders

  • Practitioner: Provides technical knowledge & skills
  • Project Manager: Plans, organizes, communicates with client & upper management, motivates team
  • Client: Specifies requirements; interacts with product post-release
Management ≠ Leadership: Management = controlling individuals to accomplish a goal. Leadership = inspiring individuals. A project needs BOTH — poor management OR poor leadership can cause project failure.
02 Project Scheduling & Critical Path Method (CPM) Calculation-Heavy
★ CPM problems are almost certainly in the exam — master forward/backward pass

Key Scheduling Terms

TermDefinition
Critical PathLongest path in project; any delay here delays the whole project
SlackHow much a task can be delayed without delaying the project
MilestoneAn important date in the schedule
ESEarly Start — earliest a task can begin
EFEarly Finish = ES + Duration
LFLate Finish — latest a task can finish without delay
LSLate Start = LF − Duration
SlackLS − ES (or LF − EF); = 0 means critical task

4 Types of Task Dependencies

TypeNotationMeaningExample
Finish-to-StartA FS BFinish A to start BBuild wall → Paint wall
Finish-to-FinishA FF BFinish A to finish BStop engine → Stop car
Start-to-FinishA SF BStart A to finish BNight shift starts → Day shift ends
Start-to-StartA SS BStart A to start BStart engine → Start car
FS is the most common dependency type. If not specified, assume FS.

CPM — 6-Step Process

1
List all tasks and their durations
2
Determine FS dependencies
3
Draw the PERT diagram
4
Forward Pass: Calculate ES and EF for each task (left → right)
5
Backward Pass: Calculate LF and LS (right → left)
6
Find critical path (tasks with Slack = 0)
FORWARD PASS RULES EF = ES + Duration
ES (start tasks) = 0
ES (other tasks) = Max(EF of all preceding tasks)

BACKWARD PASS RULES LS = LF − Duration
LF (end task) = EF (end task) = Project Deadline
LF (other tasks) = Min(LS of all succeeding tasks)

SLACK Slack = LS − ES = LF − EF
Critical Task ⟺ Slack = 0

Solved Example (from slides)

After forward + backward pass: Strict deadline = 13 days
Critical Path: A → D → G → J (all have Slack = 0)
Task E has the most slack (8 days — it can be delayed greatly without impact).

Classic Scheduling Mistakes

  • Making an overly optimistic schedule
  • Failing to monitor and update the schedule
  • Adding people to a late project (Brooks' Law — makes it later!)
  • Leaving a task out of the schedule

Resource Leveling

Process of resolving overallocation (one person assigned to multiple tasks at the same time). Fixed by introducing fake dependencies (making parallel tasks sequential) or splitting resource usage. May delay the project.

03 Earned-Value Management (EVM) Formula-Heavy
★ EVM calculations appear in almost every exam — memorize all 6 formulas

Core Concepts

TermSymbolDefinition
Planned ValuePVValue of work planned to be done by now
Earned ValueEVValue of work actually accomplished (at budget rate)
Actual CostACMoney actually spent so far
Budget at CompletionBACTotal planned budget = Sum of all PVs
ALL EVM FORMULAS SPI = EV / PV → Schedule Performance Index
CPI = EV / AC → Cost Performance Index
SV = EV − PV → Schedule Variance
CV = EV − AC → Cost Variance
EAC = BAC / CPI → Estimated Cost at Completion
SPI < 1 → Behind schedule  |  SPI = 1 → On schedule  |  SPI > 1 → Ahead
CPI < 1 → Over budget  |  CPI = 1 → On budget
Negative variance = BAD  |  Zero/Positive variance = Good
In a perfect project, EV = AC.

Solved Example 1

PV = $50 (planned to buy by now) · EV = $50 (bought) · AC = $60 (spent $60)

SPI = 50/50 = 1.0 (on schedule)
CPI = 50/60 = 0.83 (over budget; getting 83¢ of work per $1)
SV = 50 − 50 = $0
CV = 50 − 60 = −$10 (bad)
EAC = 200/0.83 = $240.96

Solved Example 2 (Week-Based)

PV = $18 + $10 + 80%×$20 + 15%×$40 = $50
EV = $18 + 80%×$10 + 70%×$20 + 0%×$40 = $40
AC = $45 (given)

SPI = 40/50 = 0.8 → behind schedule
CPI = 40/45 = 0.89
SV = −$10 · CV = −$5
EAC = 88/0.89 = $98.88
EV uses the budgeted cost of work done — NOT the actual cost. If a task was budgeted $20 but you spent $30, its EV contribution is $20 × (% complete).
04 Process Models Conceptual

Generic Process Model — 5 Framework Activities

"Can People Make Cool Deliverables?"

Communication → Planning → Modeling → Construction → Deployment

ActivityWhat Happens
CommunicationTalk with client; gather requirements
PlanningSchedule project; estimate cost; define budget
ModelingAnalyze requirements; design algorithms & flowcharts
ConstructionCode + test software components
DeploymentDeliver to client; collect feedback; maintain

4 Process Flows

  • Linear: Each activity done once, sequentially
  • Iterative: Repeat one or more activities before moving on
  • Evolutionary: Circular; each cycle produces a more complete version
  • Parallel: Two or more activities run simultaneously

Prescriptive Process Models — Comparison Table

ModelBest ForKey FeatureAdvantageDisadvantage
Waterfall Small projects, fixed requirements Linear, sequential Simple, easy to manage No iteration; late testing = high risk
Incremental Client wants quick core product Delivers working "increments" Flexible; early delivery; lower initial cost Hard to break into increments; total cost high
Prototyping Vague/unclear requirements Build prototype → get feedback → refine Client involvement; early error detection Can slow process; scope creep risk
Spiral High-risk, uncertain projects Incremental + risk analysis each loop Rigorous risk management; flexible Costly; needs risk expertise
Incremental: Requirements known upfront; refined per increment.
Evolutionary (Prototyping/Spiral): Requirements allowed to evolve and change over time.

Waterfall — When to Use

Only when: requirements are well-defined and stable before the project starts + project is small.

Spiral Model — What Makes it Unique

Unlike all others, the Spiral model explicitly incorporates risk analysis in every loop. First loop → basic prototype. Subsequent loops → increasingly mature versions.

05 Agile Development High Yield
★ Know all 12 principles, and compare XP vs Scrum vs Kanban

Why Agile?

Traditional models are too slow for modern fast-paced business. Agile focuses on rapid, incremental delivery with continuous client communication.

12 Agile Principles (Agile Manifesto, Kent Beck et al., 2001)

  1. Highest priority: early and continuous delivery of valuable software
  2. Welcome changing requirements, even late in development
  3. Deliver working software frequently (weeks to months)
  4. Developers and client must work together daily
  5. Build projects around motivated individuals; trust them
  6. Most efficient communication: face-to-face
  7. Working software is the primary measure of progress
  8. Promote sustainable development at constant pace indefinitely
  9. Continuous attention to technical excellence and good design
  10. Simplicity — maximize the work NOT done
  11. Best results from self-organizing teams
  12. Regularly reflect on how to become more effective (retrospective)

Agile Process Model Comparison

FeatureXPScrumKanban
IterationsYes (releases)Yes (sprints: 2–4 weeks)No (continuous flow)
TimeboxedYesYesNo
RolesPair programmersScrum Master, Product OwnerAgile Coach
Special PracticePair programming, test-firstDaily Scrum meeting, retrospectiveKanban board, pull system
FocusCode simplicity + clientSprint adaptabilityFlow visualization
DisadvantageNeglects design; no docsWorks best for small teamsNo timeframe → delays

Scrum Key Terms

  • Sprint: One iteration (2–4 weeks) of development
  • Product Backlog: All client requirements for the project
  • Sprint Backlog: Requirements chosen for this sprint
  • Daily Scrum: Daily sync meeting; discuss plans and progress
  • Scrum Master: Usually the project manager
  • Product Owner: Basically the client
  • Tickets: Subtasks tracked on the Scrum board
  • Retrospective: Review of the sprint; improves next sprint

Scrum Sprint Lifecycle

1
Review Product Backlog; select items for sprint → Sprint Backlog
2
Work through 4 phases: Planning → Implementation → Product Review → Retrospective
3
Deliver completed portion; unfinished items go back to Product Backlog

Kanban

Japanese: 看板 = signboard visible to all. Focus: visualize all work; everyone is always updated. Tasks are put on Kanban cards on a Kanban board (To-Do | In Progress | Done). Pull system: participants pull work when available.

Scrum = Sprint-based (iteration); Kanban = Continuous flow (no sprint). Both use pull system and retrospectives.

XP — Extreme Programming

Created by Kent Beck. Key practices: pair programming (2 devs, 1 computer), test-first coding, user stories, simple design. Values: communication, simplicity, feedback, respect, customer satisfaction.

06 Refactoring & Code Smells Design Quality

What is Refactoring?

Changing software's internal structure without changing its external behavior. Also called: "Improving the design after it has been written."

NOT the same as performance optimization (which may make code harder to read). Refactoring makes code easier to understand and modify.

Why Refactor?

  • Improves design (prevents design decay)
  • Makes code easier to understand
  • Helps find and prevent bugs
  • Helps you program faster (good design = progress)

When to Refactor? — Rule of Three

Three "strikes" and you refactor. Also refactor: when adding a new feature, when fixing a bug, during code review.

Bad Code Smells (Martin Fowler)

SmellProblemQuick Example / Fix
Duplicated CodeChange one copy but not others → bugsExtract into shared method
Long MethodHard to understand and testExtract smaller methods
Large ClassTries to do too much; low cohesionExtract Class
Long Parameter ListHard to remember order; error-proneIntroduce Parameter Object
Divergent ChangeOne class changes for many reasonsSplit class (related to low cohesion)
Shotgun SurgeryOne change → edits in many classesMove/consolidate related code
Feature EnvyMethod uses another class's data more than its ownMove Method to other class
Data ClumpsFields that always appear together but aren't in one classExtract to a class
Primitive ObsessionUsing primitives instead of small objectsReplace with class
Switch StatementsDuplicated switch logicReplace with polymorphism
Lazy ClassClass doesn't do enough to justify existenceInline or remove it
Message Chainsa.getB().getC().doSomething()Law of Demeter; hide navigation
Middle ManClass delegates >50% to anotherInline the delegating class
Inappropriate IntimacyClasses know too much about each other's internalsMove methods; hide fields
Data ClassClass has only fields + getters/setters; no behaviorAdd behavior OR is OK as DTO
Comments (as deodorant)Comments hide bad code rather than explain good codeRefactor so code is self-explanatory
Refused BequestSubclass ignores most parent functionality; fails IS-A testRedesign hierarchy

Key Refactoring Patterns

PatternWhat it Does
Extract MethodGroup code fragment into a named method
Extract ClassWhen one class does too much; create a new class
Extract VariableReplace complex expression with named variable
Replace Temp with QueryReplace temp variable with a method call; enables reuse
Move MethodMove method to the class it uses most (Feature Envy fix)
Replace Conditional with PolymorphismSwitch on type → use subclass overriding
Introduce Null ObjectEliminate repeated null checks; return a "null object" instead
Separate Query for ModifierSplit method with side effects into pure query + modifier
Introduce Parameter ObjectGroup related parameters into a class
Encapsulate CollectionReturn read-only view + provide add/remove methods
Replace Nested Conditional with Guard ClausesEarly returns for special cases → cleaner normal flow
Can introduce bugs if not done carefully. Always test after refactoring! Databases are hard to refactor (tightly coupled). Can't change "published" interfaces if you don't own all callers.

Making Refactoring Safe

Use named refactoring patterns (Fowler's catalog). Test constantly — write tests before refactoring, run after each step. Refactor in small incremental steps.

07 Performance Optimization & KPIs Applied

Why Performance Optimization?

In modern software: even millisecond delays can cost customers. Performance must be prioritized from the ground up, not as an afterthought.

Key Performance Indicators (KPIs) — SMART Criteria

S · M · A · R · T

Specific · Measurable · Attainable · Relevant · Time-bound

Essential Software Development KPIs

KPIWhat it MeasuresKey Detail
Delivery Time Time from task initiation to completion (lead time) Related to lead time metric
Bug Rate Number of defects found in the product High rate → problems in development process
Test Coverage % of functions/lines of code tested High coverage → thorough QA; fewer unnoticed bugs
Scope Change Index (SCI) Frequency and impact of scope changes (scale 0–100) High SCI → need better planning/requirements/change control
Change Failure Rate (CFR) Proportion of production changes that cause failures High CFR → insufficient testing
KPIs link to strategic goals. Choosing the right KPIs = managing the process effectively. They're described as "the lifeblood of software development."
