01 Introduction to Testing & Bug Basics Foundation
★ Core definitions — always asked

What Is Software Testing?

Definition: The systematic process of executing programs with the intent of finding as many defects as possible, and/or gaining sufficient confidence in the system under test.

Testing is NOT about proving your program works. It's about discovering where it doesn't work.

5 Rules That Define a Bug

#RuleCalculator Example
1Missing Specified Functionality — doesn't do what spec says it shouldPress + key → nothing happens
2Prohibited Behavior — does what spec says it shouldn'tCalculator freezes when keys are pounded
3Unspecified Actions — does something not in the specProgrammer adds sqrt feature that wasn't in spec
4Missing Obvious Requirements — doesn't do something the spec forgotNo warning when battery is low → wrong results
5User Experience Issues — confusing, slow, or just doesn't feel rightButtons too small; display unreadable in sunlight

Why Do Bugs Occur? (Root Causes)

Studies consistently show bugs come from: Specifications (most) > Design > Code

  • No spec written — many projects skip formal specifications entirely
  • Incomplete specs — lack detail or thoroughness
  • Constantly changing specs — evolve during development
  • Poor communication — spec not shared with whole team
"If you can't say it, you can't do it." — Spec bugs are the most costly because they cascade into design and code.

Cost of Bugs: Logarithmic Growth

Bug fix cost increases dramatically the later a bug is found: Specification < Design < Code < Testing < Production. Find bugs EARLY.

7 Testing Realities

RealityKey Point
1. Testing is Impossible to CompleteInputs, outputs, paths, and spec subjectivity are all huge/infinite
2. Testing is Risk-BasedNot testing every case = accepting risk; balance is key
3. Can't Prove No Bugs ExistFinding no bugs ≠ no bugs. Like a house inspector finding nothing.
4. More Bugs = More NearbyBugs cluster (bad days, repeated mistakes, design issues)
5. Pesticide ParadoxReusing same tests stops finding bugs (Boris Beizer, 1990). Keep writing NEW tests.
6. Specs Are Never FinalAssume the spec will change. Features added/removed always.
7. Not All Bugs Get FixedBusiness decisions: not enough time, too risky to fix, not worth it

Famous Bug Case Studies

  • Mars Climate Orbiter ($125M, 1999): One team used metric units (Newton-seconds); another assumed imperial (pound-seconds). Spacecraft destroyed. Lesson: errors at interface between correct subsystems.
  • Intel Pentium FDIV Bug (1994): Known before release; team decided it was too rare to fix; became massive PR disaster.
  • Excel Leap Year Bug: Excel wrongly treats 1900 as a leap year. Intentionally kept for backward compatibility — billions of spreadsheets would break if fixed.

Tester Traits

Explorer, Troubleshooter, Relentless, Creative, Perfectionist, Good Judgment, Programming Knowledge, Domain Expertise, Tactful & Diplomatic, Persuasive.

02 Classifications of Software Testing Conceptual
★ Know all 4 dimensions + "What You Already Knew" table

Dimension 1: Process (How You Test)

✅ Human-Based / Exploratory

  • No predefined test cases
  • Test design, execution, and learning happen simultaneously
  • Testers actively explore the system

📋 Criteria-Based

  • Systematic rules and measurable criteria
  • Structured; driven by clearly defined goals
  • Test cases planned in advance

Dimension 2: Knowledge (What You Know)

⬛ Black-Box Testing

  • Only knows what software should do
  • Cannot see internal code
  • Input → Output verification
  • Also: functional or behavioral testing
  • Example: Type √3.14159 in Calculator, verify output

⬜ White-Box Testing

  • Has access to source code
  • Uses code knowledge to tailor tests
  • Also: clear-box testing
  • Risk: Bias — tests may match code rather than spec

Dimension 3: Execution (Running the Program?)

🔄 Dynamic Testing

  • Program is running
  • What most people think of as "testing"

📄 Static Testing

  • Examining without running
  • Reviews, inspections, reading specs

Dimension 4: Scope (How Much?)

LevelFocusKey Question
Unit TestingIndividual function/classDoes this function work in isolation?
Integration TestingModule interactionsDo these components work together?
System TestingComplete productDoes the complete product work?
Acceptance TestingCustomer validationDoes this meet customer expectations?

What You Already Knew (Name Mapping)

What You Already DidFormal Name
Running with different inputsBlack-box testing
Tracing code line by lineWhite-box testing
Using printf to check valuesDebugging
Testing after changing codeRegression testing
Testing small units like a functionUnit testing

Test-to-Pass vs Test-to-Fail

Test-to-Pass

  • Simplest, most straightforward test cases
  • Verify software minimally works under normal conditions
  • Always run these FIRST

Test-to-Fail (Error-Forcing)

  • Deliberately designed to break the software
  • Run after test-to-pass cases succeed
Test case: A set of inputs + expected outputs (oracle) for a unit/module/system.
Test suite (test set): A set of test cases.
03 Equivalence Partitioning (EP) Calculation
★ Most exam-heavy topic — know Weak vs Strong, NextDate, Quadratic examples

Core Concept

Equivalence Partitioning: Dividing the huge (infinite) input space into groups where values inside a group behave similarly. Testing one representative from each partition is sufficient.

If all values in a partition behave identically, finding one bug from that partition reveals the same bug for all values in it. Testing (10,2), (1000,-5), (7,6) for max() when a>b — only need ONE of them.

The Two Trivial Partitions (Always Exist)

✅ Expected / Legal Inputs (E)

  • Correct format, valid range, proper type
  • Can further subdivide: E1, E2, E3…

❌ Unexpected / Invalid Inputs (U)

  • Wrong format, out of range, nonsensical
  • App must handle gracefully; further subdivide: U1, U2…

Weak vs Strong ECT

Formulas Weak ECT → Test Cases = max(|A|, |B|, |C|, ...) ← one value from each class, no combos
Strong ECT → Test Cases = |A| × |B| × |C| × ... ← ALL combinations tested

Example 1: Online Order Discount System

calculateFinalPrice(age, membershipType)

  • Age partitions: A1 (age < 18), A2 (18–60), A3 (> 60) → 3 classes
  • Membership: M1 (Regular), M2 (Premium) → 2 classes

Weak ECT → 3 test cases

  • Age < 18, Regular
  • Age 18–60, Premium
  • Age > 60, Regular

Strong ECT → 3×2 = 6 test cases

  • (A1,M1), (A1,M2)
  • (A2,M1), (A2,M2)
  • (A3,M1), (A3,M2)

Example 2: NextDate Function (3 variables)

Computes the next date. Year range: 1824–2024.

VariableEquivalence Classes
Month (M)M1: 30-day months · M2: 31-day months · M3: February → 3 classes
Day (D)D1: 1–28 · D2: 29 · D3: 30 · D4: 31 → 4 classes
Year (Y)Y1: 1900 (special centennial) · Y2: other leap years · Y3: non-leap years → 3 classes
Weak ECT = max(3, 4, 3) = 4 test cases
Strong ECT = 3 × 4 × 3 = 36 test cases

Example 3: Quadratic Equation (Behavioral Partitioning)

ax² + bx + c = 0, Discriminant D = b² − 4ac

PartitionabcExpected Result
a = 0021Linear equation (special case)
D > 0 (two real roots)156x = −2, −3
D = 0 (one repeated root)121x = −1
D < 0 (complex roots)123Complex roots
Only 4 tests cover ALL behavioral scenarios. Behavioral partitioning > range partitioning when code paths differ.

Leap Year Equivalence Classes (Exam Favorite)

ClassConditionExamplesExpected
C1Divisible by 4001600, 2000Leap year ✅
C2Divisible by 100, NOT 4001700, 1900NOT leap year ❌
C3Divisible by 4, NOT 1001996, 2024Leap year ✅

Don't over-partition — you may eliminate tests that reveal bugs. Always have an experienced tester review your equivalence classes.
04 Boundary Value Testing (BVT) Calculation
★ BVT formula + 7 boundary points are almost always tested

Why BVT?

Experience shows programmers frequently make mistakes at the edges of equivalence classes. BVT is complementary to EP — while EP picks values from within a partition, BVT picks values AT and NEAR boundaries.

if (x < 0) when it should be if (x <= 0). Only x=0 (the boundary) reveals this bug!

The 7 Boundary Points

For a valid range [LB, UB] BLB = Just BELOW lower bound (e.g., LB − 1)
LB = Lower Bound itself
ALB = Just ABOVE lower bound (e.g., LB + 1)
NOM = Nominal (typical value in middle)
BUB = Just BELOW upper bound (e.g., UB − 1)
UB = Upper Bound itself
AUB = Just ABOVE upper bound (e.g., UB + 1)

Test Case Count Formula BVT Test Cases = 4n + 1 where n = number of input variables
(For n=2: 4×2+1 = 9 test cases)

BVT: 9 Test Cases for f(x, y) where a≤x≤b, c≤y≤d

TCxy
1x_NOMy_LB
2x_NOMy_ALB
3x_NOMy_NOM
4x_NOMy_BUB
5x_NOMy_UB
6x_LBy_NOM
7x_ALBy_NOM
8x_BUBy_NOM
9x_UBy_NOM

Pattern: Hold all variables at NOM, vary one variable across all its boundary points.

Solved Example: Font Identifier

Specs: (1) Alphanumeric only, (2) 3–15 characters, (3) First 2 must be letters.

Sub-Boundary Conditions (Internal)

Boundaries that are internal to software — not visible in the spec but critical:

Powers of Two

  • Bit: 0 or 1
  • Byte: 0–255
  • Word: 0–4,294,967,295
  • Kilo = 1,024; Mega = 1,048,576

ASCII Boundaries

  • Digits: 48–57 ('0'–'9'); '/' = 47; ':' = 58
  • Uppercase: 65–90 (A–Z); '@' = 64; '[' = 91
  • Lowercase: 97–122 (a–z); '`' = 96; '{' = 123
  • Test chars just outside these ranges!

Empty / Null / Zero — Special Partition

When user hits Enter without typing anything → create a separate equivalence class for this. It follows a different code path than typing 0 or –1.

BVT tests only ONE variable at a time. Does NOT cover variable interactions. For interacting variables, use Combinatorial BVT (expensive).
05 Static White-Box Testing & Spec Review Review

Static Black-Box: Testing the Spec

Definition: Reviewing the product specification (not running code) for bugs. The spec is the earliest and cheapest place to find bugs.

8 Attributes of a Good Spec (Checklist)

C · A · P · C · R · F · C · T

Complete · Accurate · Precise/Clear · Consistent · Relevant · Feasible · Code-Free · Testable

Static White-Box: Examining Code

Definition: Carefully and methodically reviewing software design, architecture, or code for bugs without executing it. Also called structural analysis.

3 Types of Formal Reviews

TypeFormalityKey Feature
Peer ReviewLeast formalProgrammer + 1–2 others ("buddy review"). Still needs all 4 review elements.
WalkthroughMediumProgrammer formally presents code to 4–5 people; advance distribution; written report after. Include a senior programmer.
InspectionMost formalA DIFFERENT person presents the code (not the author). Requires training. Most effective at finding bugs.

06 Dynamic White-Box Testing, Code Coverage & JUnit Code
★ Statement / Branch / Condition coverage + JUnit assert methods are exam favourites

Dynamic White-Box Testing

Running the software WITH knowledge of the internal code to determine what to test, what not to test, and how to approach testing.

Unit → Integration → System

1
Unit Testing: Test each module/function individually in isolation
2
Integration Testing: Combine modules and test their interactions
3
System Testing: Test the complete integrated product

Bottom-Up Testing

  • Test low-level modules first
  • Use Test Drivers to simulate higher-level callers
  • Very thorough low-level testing

Top-Down Testing

  • Test high-level modules first
  • Use Test Stubs to simulate lower-level modules
  • Example: fake temperature sensor returns hardcoded values

Code Coverage Types (3 levels)

Coverage TypeGoalLimitationTest Cases Needed
Statement Coverage Execute every statement at least once Doesn't ensure all paths are taken Minimum; simplest
Branch Coverage Every branch (true/false of every if) executed Doesn't handle compound conditions Requires both true/false for each branch
Condition Coverage Every individual condition in compound expression tested T/F Can be expensive for many conditions 2ⁿ for n conditions (True-True, True-False, False-True, False-False)

Condition Coverage Example

IF Date$ = "01-01-2000" AND Time$ = "00:00:00" THEN ...
Date$Time$Condition
01-01-199911:11:11False-False
01-01-199900:00:00False-True
01-01-200011:11:11True-False
01-01-200000:00:00True-True ✅ (only this executes THEN)

Code Coverage Analyzers Tell You:

  • Which code was NOT covered (write more tests!)
  • Which tests are REDUNDANT (same partition — remove)
  • Which new test cases are needed

JUnit — Java Unit Testing Framework

Open-source; integrates with Eclipse. Green bar = all pass; Red bar = failure. Annotations drive test execution.

JUnit Assert Methods

MethodFails When
assertTrue("msg", condition)condition is false
assertFalse("msg", condition)condition is true
assertEquals("msg", expected, actual)values not equal (use .equals())
assertSame("msg", expected, actual)not same object (!=)
assertNotSame("msg", expected, actual)same object (==)
assertNull("msg", value)value is not null
assertNotNull("msg", value)value is null
fail("msg")Always — used for incomplete tests
Use EP and BVT to select test inputs · Test ONE thing per test method · Avoid logic (if/else, loops) in tests · Give methods LONG descriptive names · Expected value always on LEFT in assertEquals · Always include messages for better failure output
JUnit does NOT guarantee test method execution order. Tests must be self-contained — do NOT write Test A that must run before Test B.
07 System, Acceptance & Performance Testing Applied

System Testing

Evaluates the fully integrated system as a whole from the user's perspective (black-box). Verifies functional + non-functional requirements.

Types of System Testing

TypeWhat It TestsExample
FunctionalAll specified features work correctly end-to-endLogin → Search → Order → Pay flow
PerformanceBehavior under different workloads1000 users booking simultaneously
SecurityProtection from unauthorized access/attacksSQL injection, password strength, MFA
CompatibilityWorks on different browsers/OS/devicesChrome, Firefox, Safari; Windows, macOS
UsabilityIntuitive and easy for real usersCan users navigate without training?

Acceptance Testing: Alpha vs Beta

Alpha Testing

  • Conducted IN-HOUSE (dev/QA team + sometimes client reps)
  • Simulated environment
  • Developers monitor and fix issues in real-time

Beta Testing

  • Conducted by REAL USERS outside the organization
  • Real-world environment
  • Limited release; users report bugs and feedback

Performance Testing — Types

TypeGoalExample
Load TestingVerify system under EXPECTED workload5,000 expected users → does it meet SLAs?
Stress TestingFind the BREAKING POINT (exceeds normal)Ramp to 10,000 users; find when it crashes
Endurance / Soak TestingSustained load over LONG duration3,000 users for 12 hours → detect memory leaks
Spike TestingSudden SURGE in traffic1,000 → 5,000 users for 20 seconds (flash sale)
Scalability TestingHow performance changes when resources INCREASE1 server: 2K users; 2 servers: 4K users?

Key Performance Metrics

Definitions + Examples Response Time = Time from request to response (e.g., 350 ms)
Throughput = Requests processed per second (e.g., 45 req/sec = 450 req / 10 sec)
Error Rate = Failed requests / Total requests × 100% (e.g., 50/10,000 = 0.5%)
Concurrent Users = Number of users active simultaneously (e.g., 5,000 students logging in)

Resource Utilization Metrics

Monitor during perf tests: CPU (%), Memory (%), Disk I/O (ops/sec), Network Bandwidth (Mbps). Spikes = bottlenecks.

Apache JMeter (Performance Testing Tool)

Industry-standard open-source tool. Simulates virtual users; measures response time, throughput, error rate.

JMeter Structure

  • Test Plan: Top-level container for all settings
  • Thread Group: Defines virtual users (threads), ramp-up time, loop count
  • Sampler: Defines request (HTTP Request — method, path, body)
  • Listener: Captures results (View Results Tree = per-request; Summary Report = aggregates)
  • CSV Data Set Config: Feed unique credentials per virtual user

Load Test Config

  • Threads: 500
  • Ramp-Up: 60 sec
  • Loop: 10
  • → Simulates 5,000 login events

Stress Test Config

  • Threads: 1000
  • Ramp-Up: 60 sec
  • Loop: 10
  • → Push beyond capacity to find break point
08 Secure Software Development (Threats & Defenses) Security
★ CIA Triad + all 4 attack types with defenses are frequently tested

CIA Triad — 3 Pillars of Security

C · I · A

Confidentiality — Data not disclosed to unauthorized parties (even partial leakage = compromise)
Integrity — Data/code not created, modified, or destroyed by unauthorized parties
Availability — Authorized users can access system when needed (disruption = security failure)

Threat Modeling

Proactively thinking in advance about: how the system could be attacked, what's worth attacking, and what defenses to build IN BEFORE the attack.

Attack 1: Brute Force

How: Systematically try passwords until one works. No exploit needed — just repeated guessing.

Why it works: Weak passwords allowed; unlimited login attempts; no rate limiting; no lockout; no CAPTCHA/MFA.

Strong password policy (min length, complexity, screen against weak passwords) · Rate limiting + account lockout after N failures · CAPTCHA to block bots · MFA so correct password alone is insufficient

Attack 2: Denial of Service (DoS / DDoS)

DoS: Single source overwhelms system. DDoS: Botnet of thousands of compromised machines — makes source blocking ineffective.

Effect: Server handling 100 req/sec receives 10,000 req/sec → crashes or becomes unresponsive → attacks Availability (CIA).

1. Source-based Blocking — filter traffic from suspicious IPs
2. Rate Limiting — throttle requests per IP per time window
3. Traffic Filtering — inspect for anomalous patterns/signatures
4. Load Balancing + Auto-scaling — distribute traffic; no single node fails alone

Attack 3: Buffer Overflow

What: Writing MORE data into a fixed-size buffer than it can hold — excess spills into adjacent memory, overwriting other variables or return addresses.

char name[8];      // 8 bytes allocated
strcpy(name, "AAAAAAAAAAAAAAAAAA"); // 20 chars → OVERFLOW
// Adjacent memory (e.g., isAuthenticated flag) gets overwritten!

What attacker can do:

  • Skip authorization checks (overwrite auth flag to non-zero) — attacks Confidentiality & Integrity
  • Redirect execution to privileged code — attacks Confidentiality & Integrity
  • Corrupt return address → crash the service — attacks Availability
Check sizes before copying (validate input length fits buffer) · Use SAFE library functions: strncpy, fgets instead of strcpy, gets · Use memory-safe languages: Rust, Go, Java (eliminate class of bugs entirely)

Attack 4: SQL Injection

What: User input becomes part of the SQL query logic itself when queries are built by string concatenation.

-- Normal login query:
SELECT * FROM users WHERE username = 'USER' AND password = 'PASS';

-- Attack: username = "Rahim'--"  password = "anything"
SELECT * FROM users WHERE username = 'Rahim'--' AND password = 'anything';
-- The '--' comments out the password check → logs in without valid password!
Use Prepared Statements / Parameterized Queries (never concatenate user input into SQL) · Input validation and sanitization · Principle of least privilege for DB accounts · Web Application Firewall (WAF)

Summary: Attacks vs CIA Triad

AttackPrimary CIA Target
Brute ForceConfidentiality
DoS / DDoSAvailability
Buffer Overflow (skip auth)Confidentiality + Integrity
Buffer Overflow (crash)Availability

  • DoS/DDoS → Availability

JUnit Key Facts
